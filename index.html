BoatnetThe Plex Exclusive Occupant

A cryptomining crew broke into a home media server through Plex's newest critical flaw, dug in six layers deep, and spent the night fighting off a rival gang for the machine. Nobody noticed for almost fourteen hours. Here is how it worked.

Reconstructed from 426 forensic artifactsAll times CDTVictim identifiers removed

The server was found only because a monitor wouldn't turn on.

On the morning of October 28, 2026, the owner of a headless Ubuntu media box plugged in a DisplayPort monitor, got a black screen, and started troubleshooting. That fault turned out to be real and unrelated: a framebuffer console that never took over after a boot with no monitor attached. Before rebooting, though, the owner checked what was running. One line in the process table didn't fit.

A process called ksoftirqd/0 was using 398 percent of the CPU.

On Linux, ksoftirqd is a kernel thread. It belongs to root and hangs off PID 2. This one belonged to plex, the service account that runs Plex Media Server, and its executable lived in /tmp/.cache/. That single mismatch was the first sign of an intrusion that had been running since 9:50 the previous night, mining Monero for strangers on every core the machine had.

The software behind it calls itself boatnet. One of its scripts describes its job in four words: "Plex exclusive occupant."

I. The Door

Six days after the warning

On October 21, 2026, CISA added four Plex Media Server vulnerabilities to its Known Exploited Vulnerabilities catalog: CVE-2026-96652, -96654, -96655 and -96656. Together, researchers call them Plex2Shell. Criminals were already using them in the wild to plant cryptominers and proxy malware.

Six days later, this server was still running Plex 1.42.2, a vulnerable build. Its firewall allowed port 32400 from anywhere, and the router forwarded an outside port straight to it. That was all the attackers needed.

The chain needs no password, no phishing and no help from the user. It works like this:

① SSRFA crafted request to /player/timeline makes Plex fetch a URL on the attacker's behalf.
② Token theftThat loopback request carries the server owner's admin token, which ends up in the attacker's hands.
③ InjectionAs "admin," the attacker sets TranscoderH264Options, which Plex passes verbatim to x264.
④ The dropA transcode job writes a malicious .so into Plex's Codecs folder.
⑤ ExecutionPlex loads every library in that folder at startup, with no signature checks. Code runs as plex.

At 21:50:05 a file called zz55802.so appeared in the Codecs directory, next to fourteen real codec libraries that were all dated July 15. It weighed 1,036,800 bytes, about the same as its neighbors. Only 155 bytes of it were code. The rest was padding, so the file wouldn't stand out by size.

The code is a single constructor that runs the moment the library loads. It decodes a 1,976-byte shell script and pipes it to /bin/sh. Because the file lives in Plex's writable data directory and not in the installed package, dpkg -V plexmediaserver reported the installation as clean throughout the intrusion. The backdoor sat entirely outside what the package manager checks.

Investigators later recovered the environment of the first malicious process and found its working directory still pointing inside a live Plex transcode session:

HOME=/tmp
PWD=/tmp/plex-transcoder/Transcode/Sessions/plex-transcode-<redacted>
BOAT_LOCK_FD=200

That ties the first execution directly to the exploit path, independent of any file timestamp.

II. The Crew Moves In

Fifty-six seconds to persistence

The dropper wasted no time. It killed a dozen known rival miners by name (xmrig, kinsing, kdevtmpfsi, pwnrig, plus a few with names like mylovelyminer). Then it pulled down its loader from a server at 176.123.7[.]7, launched it, and sent a "landing" beacon home. If wget and curl weren't available, it fell back to opening a raw TCP socket from bash.

The loader is the core of the operation: a statically linked, UPX-packed ELF with its section-header table removed to frustrate analysis. It disguises itself as [kthreadd], the parent of every real kernel thread. It names itself boatnet-unit-v2 and its shell hooks # boat-rc.

Within one second it had rewritten the plex user's crontab. Fifty-six seconds after the exploit landed, cron ran the loader for the first time. Before anyone noticed, cron had run it 304 times.

  1. Oct 27 · 21:50:05Exploit library lands in the Plex Codecs folder and runs.
  2. 21:50:16Crontab replaced; shell-startup hooks written; first polymorphic copies staged in /dev/shm, /var/tmp and /tmp.
  3. 21:51:01First cron run of the loader.
  4. 22:03 – 22:20Loader tries to fetch the miner, logs fetch_all_fail, and keeps retrying.
  5. 22:23:30Mining begins. 8 threads, about 1,200 hashes per second, to MoneroOcean over TLS.
  6. Oct 28 · 01:49 – 08:19About 116 mutated loader copies written across three temp filesystems.
  7. 08:19A file named .kpx appears. It is on the crew's own list of rivals to destroy.
  8. 10:30A new generation arrives, disguised under Plex's own binary names.
  9. ~11:30Owner spots ksoftirqd/0 at 398% CPU while troubleshooting the monitor.
  10. 12:37After three cleanup rounds the host verifies clean. Load average: 0.39.

III. Six Layers Deep

Built to survive a reboot, a kill, and an upgrade

Most cryptojackers are disposable. Kill the process, delete the binary, and they're gone. Boatnet was built on the assumption that someone would try exactly that.

Layer one: the crontab. Six entries. Two loader paths run every three minutes, a watchdog runs every minute, and three staggered @reboot lines run on startup. The watchdog rewrites the crontab every 60 seconds, so deleting the entries does nothing while it's alive.

# the plex crontab, as found
*/3 * * * * /tmp/.cache/.cpuhp690 >/dev/null 2>&1
@reboot sleep 15; /tmp/.cache/.cpuhp690 >/dev/null 2>&1
*/3 * * * * /var/lib/plexmediaserver/.cache/.cpuhp690 >/dev/null 2>&1
@reboot sleep 15; /var/lib/plexmediaserver/.cache/.cpuhp690 >/dev/null 2>&1
*  * * * * /var/lib/plexmediaserver/CrashUploader …/PlexScriptHost app-plex
@reboot sleep 8;  /var/lib/plexmediaserver/CrashUploader …/PlexScriptHost app-plex

Layer two: a heartbeat watchdog. A small shell loop checks the loader's heartbeat file every 45 seconds. If the heartbeat is more than three minutes old, it kills the stale process and starts a new one.

Layer three: the exploit itself. zz55802.so stayed in the Codecs folder, and Plex loads it on every start. When the owner upgraded Plex to a patched build partway through the cleanup, the malicious library was still there. The patched binary would have loaded it on the next restart.

Layer four: a hijacked plugin. The crew replaced the helper binary inside PlexScriptHost.bundle, a legacy plugin directory that the Plex package doesn't own. Reinstalling or upgrading Plex never touches it. Nearby leftovers like PBS Kids.bundle and CouchPotato.bundle made it look old and legitimate.

Layer five: shell startup files. The dropper had set HOME=/tmp, so the crew wrote identical 87-byte .bashrc, .profile and .bash_profile files there. Any shell inheriting that environment would relaunch the loader.

Layer six: systemd user units. A cpuhp690.service with Restart=always was staged in two places. It was inert, because the plex user has no lingering session to start it, but it was ready if that ever changed.

A reboot would not have fixed this machine. It would have reinstalled the infection within seconds.Forensic finding, §7

IV. A Shape-Shifter

Every download, a new fingerprint

Each time the loader downloaded itself again, it came back slightly different. Investigators cataloged six variants between 473,610 and 473,826 bytes. Each differed by only a few dozen bytes, and each had a completely different SHA-256 hash.

That was enough to defeat the response three times. A first hash sweep skipped /dev/shm. A second used a hash list that missed one variant. A third, with every known hash, still reported the system clean while 116 copies remained on disk. Only a pattern search for .b<PID> and .dl<PID> filenames in the temp directories found them all.

The disguises were layered too. Loader threads showed up as [kthreadd]. The miner called itself ksoftirqd/0 and overwrote its command line with 42 newline characters. A later generation took the names of Plex's own helpers: CrashUploader, PlexScriptHost, PlexTunerService. A cgroup escape function moved the processes out of Plex's service cgroup, so systemctl stop wouldn't reach them:

escape() {
  echo $$ > /sys/fs/cgroup/cgroup.procs 2>/dev/null || true
  echo $$ > /sys/fs/cgroup/init.scope/cgroup.procs 2>/dev/null || true
  for d in /sys/fs/cgroup/*/cgroup.procs; do echo $$ > "$d" 2>/dev/null; done
}

V. The Turf War

"Keep ksoftirqd (ours)"

The most revealing part of boatnet isn't aimed at the defender. It's aimed at other criminals.

The watchdog script, named CrashUploader to look like Plex's crash reporter, is a 3,573-byte shell program that runs every 0.2 seconds. Its header calls it the "Plex exclusive occupant." Most of its code exists to make sure no other crew can share the box.

rival() { case "$1" in
  *18899*|*plex_deploy*|*pd.sh*|*pd2.sh*|*pd3.sh*) return 0 ;;
  *130.94.112*|*89.125.187*|*PLEX_FORCE_RESTART*|*PLEX_PROXY_ONLY*) return 0 ;;
  *systemctl*restart*plex*|*killall*Plex*|*pkill*Plex*) return 0 ;;
esac; return 1 }

It kills any process matching a rival's tooling. It sabotages a rival's drop paths: as an unprivileged user it replaces them with symlinks to /dev/null, and as root it makes them immutable with chattr +i. When running as root it also adds firewall rules blocking a rival's network range and port 18899. It even blocks commands that would restart Plex, because a restart could hand the box to whoever got their payload in first.

At the same time, a whitelist function called ours() protects Plex Media Server, the Plex Transcoder, ffmpeg and EasyAudioEncoder. The crew wanted the media server healthy. A working Plex keeps the owner from looking closely, and Plex is also the crew's way back in.

"Plex uid only. Exact comm, never pkill -f. Keep ksoftirqd (ours)."Comment in the boatnet fallback dropper

The rivalry wasn't hypothetical. At 08:19 on October 28, a 473,676-byte file named .kpx showed up on the host. The name is on boatnet's own kill list. At least two separate crews exploited the same open Plex port that night. What the second crew did, and when it arrived, was never determined. It remains the biggest open question in the case.

VI. The Take

A few cents of Monero

The miner is a rebranded build of XMRig 6.26.0, from the MoneroOcean algorithm-switching fork, renamed kswap. It ran eight threads on a four-core Ryzen 3 5300U, held a 2.3 GB RandomX dataset in memory, and submitted shares over TLS to MoneroOcean pools in the US, Germany, the Gulf and Singapore. Its developer donation was set to zero.

Over about 13 hours of mining, at roughly 1,200 hashes per second, the expected payout is on the order of 0.0001 to 0.0002 XMR, a few US cents, paid to wallet 851PGy…Yq8b.

That number explains the business model. One home server is worth almost nothing. Thousands of them, compromised automatically during the window between a KEV listing and a patch, add up. So does what the crew got along the way.

What the attackers actually held

  • The Plex owner's admin token (PlexOnlineToken), stolen as part of the exploit itself. Removing the malware does not revoke it.
  • Every secret readable by uid 997. On this host, Prowlarr, Radarr, Sonarr and SABnzbd all ran as the same user as Plex, and three of their config files were world-readable.
  • A foothold good for more than mining. The same access could have been used for proxyware, ransomware staging or account takeover.

The owner was lucky that no root escalation or data exfiltration was found. But no packet capture covers the dwell period. At the moment of capture, three command-and-control channels that weren't in the loader's visible strings were open and had data waiting to send.

VII. The Cleanup

Three rounds, five mistakes, one lesson

The response got the most important things right. It collected evidence before killing anything: 426 files, including 13 process images recovered from /proc/PID/exe (three of them for binaries already deleted from disk) and a live socket table. It also stopped cron before killing processes, which is the only order that works against a watchdog that rewrites the crontab every minute.

It also made mistakes, and the forensic report documents them on purpose:

#What went wrongConsequence
1A legitimate remote Plex viewer's IP was blocked as "C2"The malware had only inherited that viewer's socket. The block was reversed.
2Three hash sweeps reported "clean"116 polymorphic copies were still on disk.
3Every uid-997 process was killed with kill -9Took down the *arr stack and two Docker containers along with the malware.
4A Mesa VA-API symlink was misread as a truncated ELF and deletedRestored once noticed.
5Evidence samples were grabbed by file sizeSome harmless JPEGs ended up in the malware bin.

The lesson is the one behind the third "clean" verdict. Against polymorphic malware, hashes give you a lower bound, not proof of absence. The approach that worked turned the attacker's own trick around. Once cleanup was done, every remaining plex process had to sit inside a legitimate system.slice unit. Anything that had escaped its cgroup stood out.

VIII. What Should Have Caught It

Fourteen hours of a CPU at full load, and silence

Load average sat around 5 on a four-core machine for most of a night and a morning, and nothing raised an alert. These checks would each have caught boatnet early:

Detections that would have worked

  • Any non-root process named like a kernel thread (kthreadd, ksoftirqd, kworker, cpuhp).
  • Any process whose /proc/PID/exe resolves into /tmp, /var/tmp or /dev/shm.
  • Any .so in the Plex Codecs folder not matching lib*_{decoder,encoder}.so.
  • A plex crontab of any size. The normal state is none.
  • Sustained high CPU from a service account.
  • The strings boatnet, boat-rc, BOAT_LOCK_FD, Plex exclusive occupant, app-plex.

If you run Plex

  1. Patch to 1.43.3.10861 or later and turn on automatic updates.
  2. Don't expose port 32400 to the internet. Use Plex Relay or keep it LAN-only.
  3. If you were exposed on a vulnerable build, assume your token is gone: sign out all devices on plex.tv, change your password, and enable 2FA.
  4. Rotate API keys for every service that shares Plex's user account, and give each service its own uid.
  5. Mount /tmp, /var/tmp and /dev/shm noexec.
  6. Remove legacy plugin bundles you don't use. That writable directory is where this crew hid.
