1Executive summary

At 21:50:05 CDT on 2026-10-27, an unauthenticated remote attacker weaponized the Plex2Shell vulnerability chain (CVE-2026-96652, CVE-2026-96654, CVE-2026-96655, CVE-2026-96656 — added to the CISA KEV catalog six days earlier, on 2026-10-21) against an internet-exposed Plex Media Server 1.42.2.10156-f737b826c on host media-server. The chain abuses an SSRF in /player/timeline to exfiltrate the server owner's admin token, then injects attacker options into the x264 transcoder to write a malicious shared object into Plex's Codecs directory — which Plex loads unverified at startup. The result: unauthenticated remote code execution as the plex service account (uid 997), without touching a single package file (dpkg -V plexmediaserver remained clean).

The payload was a Monero (RandomX) mining operation of unusual sophistication for a "mere miner": a constructor-driven dropper staged a UPX-packed, polymorphic, self-healing loader ("boatnet") disguised as kernel threads ([kthreadd]), which installed six independent persistence mechanisms, rewrote the plex crontab every 60 seconds, evaded cgroup-based service stops, defended the host against a rival mining crew, and finally downloaded and supervised a rebranded XMRig miner (ksoftirqd/0) mining to MoneroOcean pools at ~1,200 H/s across 8 threads.

The intrusion ran undetected for 13 hours 45 minutes. It was discovered incidentally — while the operator troubleshot an unrelated display fault, a process-table check revealed a ksoftirqd/0-named process owned by plex burning 398% CPU. No monitoring alert had fired despite a load average of ~5 sustained for hours.

It could have been much worse — and the guardrails were partly luck, not design. The miner kept the media server alive (it whitelisted Plex processes to preserve its own re-entry path), no root escalation was observed, and no data exfiltration was identified. But the attacker did hold the Plex owner's admin token and every service credential readable by uid 997 for nearly 14 hours, and the persistence was engineered to survive reboots, process kills, and even a Plex package upgrade.

Because six unrelated services run as uid 997, "owned by plex" is not an indicator of compromise on this host. 3Detection narrative — found by accident

The compromise was not detected by any control. The sequence:

  1. The operator reported the physical console would not wake on a DisplayPort monitor and asked whether the system ran headless. It does (multi-user.target, no X/Wayland).
  2. Display diagnosis found an unrelated genuine fault: the machine booted with no monitor attached (amdgpu: Cannot find any crtc or sizes), and when a monitor was attached at 11:00:56 on 2026-10-28 the kernel logged fbcon: Deferring console take-over — with deferred-takeover enabled and Plymouth never handing off, tty1 wrote to a dummy console driver. Fix staged (fbcon=nodefer in /etc/default/grub) but not yet applied.
  3. While checking whether a reboot was safe, ps showed a process consuming 398% CPU, owned by plex, with comm = ksoftirqd/0.
  4. Real kernel threads are root-owned children of PID 2. This one had exe → /tmp/.cache/ksoftirqd and uid 997. That single discrepancy exposed the intrusion.
Detection gap

Sustained ~400% CPU and load ~5 persisted for hours with zero alerting — no anomaly detection on CPU, no alert on non-root processes bearing kernel-thread names, no alert on executable writes to /tmp, /var/tmp, /dev/shm, and no alert on a previously-empty user acquiring a crontab.

4Entry vector — the Plex2Shell chain

Plex2Shell chains four flaws in Plex Media Server before build 1.43.3.10861 into unauthenticated RCE as the server account. CISA added all four CVEs to the Known Exploited Vulnerabilities catalog on 2026-10-21, following in-the-wild exploitation delivering cryptominers and proxy malware. This host was compromised six days later — a textbook KEV-lag window.

4.1 Corroborating local evidence

  • The dropped zz55802.so sat in the Codecs directory timestamped 2026-10-27 21:50:05, among 14 legitimate codec libraries all dated 2026-07-15 and all matching lib*_{decoder,encoder}.so.
  • All malicious execution was uid 997, never root — matching "code execution as the account running the server."
  • Malicious processes held inherited file descriptors to Plex's own client sockets (fd 88 → an established Plex client session on :32400; fd 91 likewise), proving they were spawned from within the Plex process tree rather than via a separate service.
  • dpkg -V plexmediaserver: no deviations.

4.2 Smoking gun — exploit provenance in the loader's environment NEW FINDING

The environment block recovered from the first loader instance (pid 1327450, started 21:50:15) preserves its original working directory and argv0:

PWD inside a live Plex transcode session directory is direct, process-level proof that the first execution originated from the transcode/exploit path — corroborating the CVE-2026-96656 mechanics independently of file timestamps. BOAT_LOCK_FD=200 shows the loader reserves a high fd for its lock, and HOME=/tmp (from the stage-1 payload) is what later makes the shell-rc persistence in /tmp functional (§7.3).

Survivability note

This component survived containment round 1 and the operator's Plex upgrade: it lives in writable state under /var/lib, which the package manager neither owns nor overwrites. Had Plex been restarted between round 1 and round 2, re-infection was certain — the upgraded, patched binary would have re-loaded the malicious .so on boot.

6.2 Stage 2 — loader / bot "boatnet" UPX-packed ELF

A statically linked x86-64 ELF with no section-header table (deliberate anti-analysis), packed with UPX (packer signature string present) and further string-obfuscated. Plaintext survivors include only /proc/self/exe and the four C2 endpoints 176.123.7.7:80/:443, 80.87.206.86:80/:443 — the rest of its configuration is packed/encrypted, which is why its live C2 channels (§9) were only visible in the socket table. Self-identifies as boatnet-unit-v2 / # boat-rc; lock file .boat.lock; heartbeat .cpuhp690.beat. Its environment preserves BOAT_LOCK_FD=200 and the transcode-session PWD (§4.2).

7Persistence mechanisms

Six independent mechanisms were deployed. Four survived containment round 1 — the initial kill-and-delete pass removed the running processes and primary payloads but not the deeper hooks.

7.1 The plex crontab (primary, active)

*/3 * * * * /tmp/.cache/.cpuhp690 >/dev/null 2>&1
@reboot sleep 15; /tmp/.cache/.cpuhp690 >/dev/null 2>&1
*/3 * * * * /var/lib/plexmediaserver/.cache/.cpuhp690 >/dev/null 2>&1

Three @reboot entries plus the Codecs-dir .so (re-fired by Plex itself on start) plus the plugin-bundle helper mean a clean shutdown/restart cycle would have restored the full infection within seconds of boot.

7.2 Backdoored plugin bundle — the upgrade survivor

…/Plug-ins/PlexScriptHost.bundle/Contents/Helpers/PlexScriptHost (473,826 B) replaced with the loader. PlexScriptHost.bundle is not shipped by the plexmediaserver package — dpkg -L has no entry — so neither reinstall nor upgrade touches it. Legacy plugin bundles (PBS Kids.bundle, CouchPotato.bundle remain) give this directory the perfect camouflage of age and legitimacy.

7.3 Shell-rc persistence

# boat-rc — /tmp/.bashrc, /tmp/.profile, /tmp/.bash_profile (identical, 87 B)
[ -x "/tmp/.cache/.cpuhp690" ] && "/tmp/.cache/.cpuhp690" >/dev/null 2>&1 &

Effective because the stage-1 payload exports HOME=/tmp, so any shell the malware (or an operator inheriting that environment) starts sources these files.

7.4 systemd user units — staged but inert

cpuhp690.service (# boatnet-unit-v2, Restart=always, RestartSec=20) placed in both /tmp/.config/systemd/user/ and the plex home. Assessed inert: no *.wants symlinks, and loginctl show-user plex reported "not logged in or lingering" — no user manager would ever start them. Removed regardless.

10Evasion & adversary capabilities

10.1 Polymorphism — defeats hash-based detection

Every loader download produced a mutated binary: six distinct SHA-256 values across sizes 473,610 / 473,612 / 473,628 / 473,645 / 473,676 / 473,826 bytes. Consequence, demonstrated three times during the response itself: hash sweeps reported "CLEAN" while 116 copies remained on disk. Detection on this family must be behavioral or pattern-based (name/size/location heuristics), never hash-based. The binary additionally strips its section-header table and is UPX-packed, degrading static analysis.

10.2 Process masquerading

  • Loader threads set comm to kthreadd and render as bracketed [kthreadd] — the genuine PID-2 kernel thread.
  • The miner uses ksoftirqd/0 and overwrote its cmdline with 42 newline bytes (not merely empty — the classic XMRig argv-overwrite trick).
  • Masked-name generation impersonates Plex's own binaries: CrashUploader, PlexScriptHost, PlexTunerService in the plex home directory.
  • Tells on this host: non-root ownership, exe symlink into /tmp, PPid 1, and empty/newline cmdlines.

10.3 cgroup escape

escape() {
  echo $$ > /sys/fs/cgroup/cgroup.procs 2>/dev/null || true
  echo $$ > /sys/fs/cgroup/init.scope/cgroup.procs 2>/dev/null || true
  for d in /sys/fs/cgroup/*/cgroup.procs; do echo $$ > "$d" 2>/dev/null; done
}

Detaches the malware from the service cgroup so systemctl stop and per-unit resource limits never reach it. The response used this in reverse: post-remediation, every remaining plex process sat inside a legitimate system.slice unit — cgroup membership became the verification signal.

10.4 Rival eviction & host preservation

Kill-lists over process/command patterns and iptables REJECT rules against rival networks, plus booby-trapped rival drop paths (ln -sfn /dev/null as plex; chmod 000 + chattr +i as root). Simultaneously a self-preservation whitelist (ours()) keeps genuine Plex Media Server, Plex Transcoder, ffmpeg, EasyAudioEncoder alive — the crew wants the media server (and its re-entry path) healthy.

10.5 Privilege-conditional behavior

fw() and the hardening branch of trap_drop() are gated on [ "$(id -u)" = 0 ]. No iptables REJECT rules for 18899 / 130.94.112.0/24 / 89.125.187.222 existed in iptables-save — consistent with the malware never having run as root.

15Investigation limitations

  • No data-exfiltration determination. Egress volume was not reconstructed; no packet capture exists for the dwell period. The pending send queues on the C2 channels (285 B / 3,018 B) and a 229,944-byte EasyAudioEncode queue (legitimate client streaming) were not deep-inspected.
  • No reverse engineering of the loader. Classification rests on strings, ELF structure, runtime behavior and scripts. The UPX-packed loader may have capabilities not described here — notably, the protocols spoken to the three newly attributed C2 endpoints (§9) are unknown.
  • No root-compromise proof, only absence of evidence. Supporting "no escalation": all artifacts uid 997; dpkg -V clean; no new authorized_keys; no root crontab; no malicious system units; root-gated malware branches never executed. Not performed: full package verification, kernel-module integrity check, rootkit scan (rkhunter/chkrootkit were never run).
  • Volatile evidence partially lost. Round 1 killed processes ~90 minutes after detection; no memory image was captured. Only /proc metadata and recovered exe images survive.
  • Log coverage incomplete. Kernel ring buffer wrapped (61-day uptime); opensnitchd was running but its logs, while mentioned in the original manifest, were not present in the collected set and were never analyzed — they would be the first place to look for per-connection egress history.
  • Rival-actor scope unassessed. The .kpx sample survives, but what the second actor did and when it first landed was never established.
  • Chain-of-custody caveat. All evidence was collected live from the compromised host by a root shell — not a forensic disk image. Timestamps and tool output could in principle have been manipulated by a sufficiently privileged attacker, though no evidence of root access was found.
